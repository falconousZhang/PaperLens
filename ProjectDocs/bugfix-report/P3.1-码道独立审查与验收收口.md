## 问题

1. ReviewResult 批次先提交，任务 SUCCEEDED 状态后提交；第二次提交失败时会留下成功结果和失败任务，违反原子性。
2. 4 个 API 的路径参数使用普通字符串，非法 UUID 可能进入数据库层并产生 500。
3. 测试通过全局 `set_llm_client/reset_llm_client` 替换客户端，并发请求和并发测试可能互相污染。
4. 审阅查询只按 paper 查询结果，再在 Python 中检查任务用户；任务缺失或归属不一致时边界不可靠。
5. 创建任务请求接受未知字段、默认 task_type 和任意 language，Top-K 配置没有上限。
6. 论文标题和 Evidence 原文可包含 Prompt 边界闭合标签，模型可能把不可信内容误解为系统指令。
7. 重复 alias 可以生成重复关联；rating/confidence 对字符串存在隐式类型转换。
8. 自定义 Pydantic 校验错误的 `ctx` 含 ValueError 对象，统一错误处理直接返回 `exc.errors()` 时无法 JSON 序列化，非法请求变成 500。
9. 文档中的维度名、测试数量、当前/规划状态与真实实现不一致；码道还越界还原了两个 码道提示词文件。

## 根因

1. 初版只覆盖正常路径和首维失败，没有覆盖第二维失败后的整批事务状态。
2. API 契约和服务层验证分散，缺少统一 UUID4、严格 schema、用户归属和 JSON-safe 错误边界。
3. Mock 依赖采用进程级可变状态，没有利用 FastAPI dependency override 或显式服务参数。
4. Prompt 将数据库原文直接插入结构化标签，未将其视为不可信输入。
5. 码道以自身测试通过作为完成标准，没有再次核对禁止范围、文档事实和失败路径。

## 修正

1. ReviewResult/Finding/关联和 SUCCEEDED 状态改为同一事务提交；异常统一回滚后单独记录 FAILED。
2. API 路径参数统一为 UUID4，并保持统一 422 错误结构。
3. 删除全局可变 LLM 替换器；API 通过依赖注入取得客户端，服务支持显式传入客户端。
4. 审阅结果在 SQL 中连接 AnalysisTask 并同时过滤 paper/user；Evidence 绑定额外限制同一 paper。
5. 请求和 LLM 输出 schema 使用 `extra=forbid`、Literal、严格数值、数量边界和重复维度校验。
6. 论文标题与 Evidence 文本进行 HTML 转义，系统提示明确标签内容均为不可信论文数据。
7. 对合法重复 alias 去重，确保一个 Evidence 只建立一次关联。
8. 统一校验异常递归转换为 JSON-safe 结构，保留错误信息并稳定返回 422。
9. 补充第二维失败回滚、非法 UUID/options、跨用户隔离、候选顺序、Prompt 边界、严格类型和重复 alias 测试。
10. 校准 ProjectDocs、Sprint、实现状态和进度记录；恢复提示词归档并生成下一阶段提示词。
