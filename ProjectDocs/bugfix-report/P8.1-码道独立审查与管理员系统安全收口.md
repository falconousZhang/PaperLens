## 问题现象

码道初版的 47 项 P8.1 定向测试通过，但不同目标同时执行首次引导时可能都观察到零管理员；两个管理员互相变更时，等待请求不会在锁后重新校验操作者，存在使用旧权限继续写入的窗口。旧 `promote-admin --email` 仍可绕过首次管理员、会话撤销和不可变审计。审计表只限制 JSONB 为对象，不能保证 action 与精确 role/status 状态对应；管理员列表还存在逐行 N+1 和完整实体加载。管理页把外层 refresh 与子列表共用同一加载序号，进入用户、内容或审计区域后可能永久显示加载中。

## 根因

1. `FOR UPDATE` 在零结果时不会形成互斥，且认证依赖读取的操作者对象在等待锁期间可能失效。
2. P3.5 历史运维入口未纳入 P8.1 安全模型，形成第二条无审计角色提升路径。
3. 测试覆盖了同目标 bootstrap，却没有覆盖不同目标、操作者权限竞态、查询次数和精确 JSONB 状态形状。
4. 前端总刷新函数和各资源加载函数重复增加全局请求序号，外层 finally 永远无法清除 loading。

## 修复方案

- 为首次引导和管理员集合变更增加同一个 PostgreSQL 事务级 advisory lock；取得锁后按 id 锁定 ACTIVE ADMIN、操作者和目标，并重新校验操作者 ACTIVE ADMIN 状态。
- 移除旧 promote-admin 和 demo-user 归属迁移入口；admin-bootstrap 只接受 UUID4 与 reason，未知异常不透传内部信息。
- 预生成 audit id，用户、session/reset 失效与审计同事务；提交结果未知时回查目标状态和全部 audit id，不重复写入。
- 017/ORM 增加 action 对应精确 before/after JSONB CHECK，reason 去空白且拒绝控制字符；保留 UPDATE/DELETE trigger 和非空降级保护。
- 用户资源计数使用相关子查询，论文与审计使用 JOIN，任务和报告只查询安全列投影；筛选统一枚举、UUID4、分页、搜索和带时区时间。
- 修复管理页加载代数，增加用户详情、论文/任务/报告独立筛选与分页、审计筛选、reason 去空白校验、固定错误文案和窄屏布局。
- 增加不同目标 bootstrap、互相降级、严格审计状态、非法筛选、查询次数和管理员页面测试。
