## 1. 测试策略

### 1.1 测试金字塔

```
        /  E2E  \           5%  — 端到端关键路径验证
       /集成测试  \         15%  — API + DB + Storage 联动
      /  单元测试   \       80%  — 函数/组件/Service 级别
```

| 层级 | 占比 | 工具 | 目标 |
|------|------|------|------|
| 单元测试 | 80% | pytest (后端) / Vitest (前端) | 函数、Service、Vue 组件逻辑 |
| 集成测试 | 15% | pytest + Docker PostgreSQL | API → DB → Storage 端到链路 |
| E2E 测试 | 5% | Playwright (规划) | 用户关键操作路径 |

### 1.2 测试原则

1. **确定性优先**: 所有数值统计由确定性 Python 代码计算，测试不依赖 LLM 输出
2. **隔离性**: 测试使用 `paperlens_test` 独立数据库，测试后自动 TRUNCATE，不污染开发库
3. **安全优先**: 错误信息不泄露内部异常，路径穿越防护，文件类型校验
4. **Evidence 可追溯**: 每条测试断言可追溯到需求规格 (FRxx.x)
5. **0 skipped**: Docker 环境下全量测试必须 0 skipped

### 1.3 测试环境

| 环境 | 用途 | 数据库 | 说明 |
|------|------|--------|------|
| 本地开发 | 快速反馈 | SQLite / 无 DB | 非 DB 测试本地运行 |
| Docker CI | 全量验证 | PostgreSQL `paperlens_test` | `PAPERLENS_TEST_DATABASE_URL` 配置 |
| E2E (规划) | 用户路径 | 完整 Docker Compose | 前后端 + DB + Storage |

**Docker 环境关键配置**:
- 测试数据库: `paperlens_test`（通过 `PAPERLENS_TEST_DATABASE_URL` 指定）
- 每个测试 fixture 自动执行: `ensure_test_database` → `run_alembic_migrations` → `verify_alembic_revision`
- 测试结束自动: `truncate_test_tables` → `verify_no_test_residuals`
- 安全断言: Engine URL 必须包含 `paperlens_test`，否则拒绝执行

## 6. 测试执行策略

### 6.1 执行命令

| 环境 | 命令 | 说明 |
|------|------|------|
| 后端 (全量) | `docker compose run --rm backend pytest --tb=short -q` | Docker PostgreSQL, 0 skipped |
| 后端 (非 DB) | `cd backend && pytest -m "not requires_db"` | 本地快速反馈 |
| 前端 | `cd frontend && npm run test` | Vitest |
| E2E (规划) | `npx playwright test` | Playwright |

### 6.2 CI 流水线

```
代码提交
  ├── 后端单元测试 (非 DB, < 30s)
  ├── 前端单元测试 (< 15s)
  └── 后端集成测试 (Docker, < 120s)
        ├── 启动 PostgreSQL 容器
        ├── 运行 Alembic 迁移
        ├── 执行全量测试
        ├── 验证 0 skipped
        └── TRUNCATE 测试数据
```

### 6.3 测试数据管理

| 策略 | 说明 |
|------|------|
| PDF 生成 | `conftest.py` 中 `create_test_pdf` 使用 PyMuPDF 动态生成 |
| 数据库隔离 | `paperlens_test` 独立库，fixture 自动 TRUNCATE |
| 安全断言 | Engine URL 必须包含 `paperlens_test`，否则拒绝执行 |
| 残留检测 | `verify_no_test_residuals` 确保测试后无脏数据 |
| 开发库保护 | `test_dev_db_not_polluted` 验证测试不污染开发数据库 |

## 7. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| LLM 输出不确定 | 审阅测试不稳定 | 使用 MockLLMClient，仅测试结构和约束 |
| FAISS 索引跨平台 | Docker/本地结果不一致 | 统一在 Docker 环境运行集成测试 |
| PDF 样本覆盖不足 | 边界场景遗漏 | 补充多栏、数学公式、中文论文等测试 PDF |
| E2E 测试脆弱 | UI 变更导致频繁修复 | 使用 data-testid 选择器，避免依赖 CSS 类名 |
| 测试执行时间增长 | CI 反馈变慢 | 分层执行: 非 DB 快速反馈 + Docker 全量验证 |
